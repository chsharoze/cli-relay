# Audit-log integrity verification must not gate audit-log writes

Whole-history integrity verification must be a separate, read-only operation, never a prerequisite for appending an audit record. Computing a new record's hash is necessary for hash chaining; proving the entire existing history intact before accepting that record is a different operation. Coupling the two can turn one damaged entry into a persistent denial of service against both an agent's tools and the diagnostics needed to explain the failure.

This principle emerged from two independent live-execution audits of Microsoft's public `agent-governance-toolkit` (AGT), specifically its Claude Code governance hook plugin. This note draws on those reported live findings, not a new reproduction. The corresponding source explains the mechanism; cli-relay's governance ledger provides a concrete implementation and regression test of the alternative.

## How an integrity check disabled its own diagnostics

In AGT's `audit.mjs`, `appendAuditEntry` loads the existing entries and calls `verifyAuditEntries` before writing. The verifier returns false for an invalid chain, causing the append function to throw. Malformed JSON can instead throw during loading. Either way, historical damage prevents the next append. A bad hash, truncated record, or concurrent-write collision can therefore affect operations unrelated to the damaged record. This is not merely an integrity warning attached to an otherwise successful write. [AGT audit implementation](https://raw.githubusercontent.com/microsoft/agent-governance-toolkit/main/agent-governance-claude-code/lib/audit.mjs)

The consequences follow from the caller. `evaluatePreToolUse` records the policy decision before returning it. An audit failure enters its error handler, and the default `denyOnPolicyError: true` converts that failure into a hard denial. Attempting to record the failure does not restore availability: the original denial is preserved even if that further audit attempt fails. [Policy evaluation](https://raw.githubusercontent.com/microsoft/agent-governance-toolkit/main/agent-governance-claude-code/lib/policy.mjs), [default policy](https://raw.githubusercontent.com/microsoft/agent-governance-toolkit/main/agent-governance-claude-code/config/default-policy.json)

Both independent audits confirmed that this denied every subsequent hooked tool call, including AGT's own MCP diagnostics, `agt_policy_status` and `agt_policy_check_text`. Those tools were allowlisted, but the hook still had to audit their admission. An allow decision could not escape the failing append underneath it. The operator's session became inert, with no in-session tool path to inspect the damage. Recovery required manual filesystem intervention outside the tool, replacing or deleting the corrupted audit file. The failure was persistent until external repair, rather than a transient refusal.

The second audit identified an internal trigger as well. AGT caps its history with `MAX_ENTRIES`, retaining the suffix through `.slice(-MAX_ENTRIES)`. The first retained entry still references a discarded predecessor, while verification expects the first entry to reference genesis. Crossing the retention boundary therefore makes the next verification fail even when every retained record was originally valid. Normal long-term operation can manufacture the condition that disables the installation. [AGT retention and verification code](https://raw.githubusercontent.com/microsoft/agent-governance-toolkit/main/agent-governance-claude-code/lib/audit.mjs)

## Two independent paths in cli-relay

cli-relay is a persistent CLI router that dispatches fresh or resumed sessions to coding-agent backends. Its [governance ledger](../src/governance/ledger.mjs) separates record production from historical validation through two rules.

**First, append from the tail without validating history.** `appendLedgerEntry` uses the existing `withLock` to serialize writers, recovers the final physical JSONL record by scanning backward, and uses its stored hash as the new record's `previous_hash`. It computes the new record's SHA-256 hash, but neither recomputes historical hashes nor calls `verifyLedger`. Earlier corruption cannot become a failed precondition for writing the next event. Tail recovery may read multiple chunks; the claim is independence from historical verification, not strictly constant-time I/O.

If the readable tail is malformed or lacks a usable hash, the implementation warns and derives a link by hashing its contents with the domain separator `malformed-ledger-tail\0`. It preserves the damaged material instead of repairing it or refusing the append. Later verification can still report that damage. An I/O-unreadable tail is different: unavailable bytes cannot be hashed. That branch warns and attempts an append using a `GENESIS` fallback, without declaring a valid checkpoint or claiming the old history has been recovered.

Append failures themselves are caught and reported as warnings rather than propagated into backend-dispatch failures. This is best-effort recording, not a promise that records survive unavailable storage. The important boundary is that evidence-generation failure does not automatically become action denial.

**Second, verify explicitly through a read-only diagnostic.** `verifyLedger` reads the complete file and checks each record's predecessor link and computed hash. It returns the first detected problem as structured data: `totalEntries`, `intact`, zero-based `breakIndex`, one-based `lineNumber`, and a human-readable `reason`. File-read failures also become reports, although they cannot identify an entry. The [audit command](../src/commands/audit.mjs), exposed as `cli-relay audit verify`, prints the report and exits 0 for an intact ledger or 1 for a detected problem. It does not append a record as a prerequisite to reporting one.

The corruption regression in [the smoke suite](../tests/smoke.sh) exercises this boundary through real CLI subprocesses with an isolated home and a fake backend. After two successful dispatches, it changes the first record's `thread` without updating its hash. Verification reports exit 1, index 0, line 1, and a hash-mismatch reason. A subsequent dispatch succeeds and adds a third record. Repeated verification remains callable and still identifies the original break. The reported regression run passed these checks: corruption blocks neither further recording nor diagnosis, and continued recording does not conceal the damage.

Retention is handled conservatively: there is no automatic size cap. Explicit checkpoint records are supported as new genesis-linked anchors; verification checks the checkpoint's own hash, and subsequent entries chain to it. Any future truncation must establish that explicit boundary, not merely discard a prefix. Appending a checkpoint after existing damage does not erase the problem: the verifier encounters and reports the earlier break first. Checkpoints define a retained history's boundary; they do not certify missing history.

## The precise gap in adjacent work

The relevant literature gap is narrower than an absence of integrity or recovery guidance. The September 5, 2026 version of *Agent Audit Trail: A Standard Logging Format for Autonomous AI Systems*, `draft-sharif-agent-audit-trail-03`, is an individual Internet-Draft, not an IETF-endorsed standard. It specifies SHA-256 hash-chained JSON records and verification. It also addresses critical integrity-error reporting, preservation of broken chains, break locations, crash-recovery gaps, and periodic storage cross-checks. What it does not require is that whole-history verification remain outside the append path or that diagnostics stay reachable after corruption. Its pre-execution recording requirements concern when actions are recorded, a separate issue. [Internet-Draft, §§6.3 and 14.4, Appendices C.5 and C.6](https://datatracker.ietf.org/doc/html/draft-sharif-agent-audit-trail-03)

*AgenticOS: An Intent-Oriented Secure Operating System Architecture for Autonomous AI Agents* (June 2026) is a conceptual architecture. Its single explicit mention of audit-log hash chains occurs in its cryptographic security assumptions, not its Ghost Kernel responsibilities. It does not specify write-time versus read-time verification or logging-failure behavior. Rejecting unrecognized agent calls, which it does discuss, answers a different question. [AgenticOS, arXiv:2606.21129v1](https://arxiv.org/html/2606.21129v1)

Neither source articulates the operational requirement demonstrated here. Together with the reported literature search, that supports an apparent gap in the reviewed material and a concrete, experimentally motivated contribution. It does not establish worldwide novelty or justify a blanket claim about all tamper-evident-log research.

The generalizable lesson is to separate historical trust from operational reachability. A damaged chain must remain visibly damaged, but its condition must not disable the means of recording subsequent events or inspecting the failure. Authorization may independently refuse an action; an audit verifier should not accidentally acquire that authority through exception propagation. Integrity diagnostics are most necessary when integrity has failed. Their execution must not depend on proving otherwise first.
